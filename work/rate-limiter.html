A rate limiter that many servers can agree on

A limit enforced inside one server isn't a limit once you run ten of them. I built a rate limiting microservice with Spring Boot and Redis that gives every instance the same answer, and keeps alerting off the request path.

Role
Design and build
Type
Personal project
Stack
Spring Boot, Redis, AWS (EC2, ElastiCache, SQS, CloudWatch), Docker

01The problem

The classic in-memory rate limiter works until you scale out. With several instances behind a load balancer, each one keeps its own count, so a client allowed 100 requests can get 100 from every instance.

I wanted a limiter that throttles per user or per IP at high throughput, gives the same answer on every instance, and can tell other systems when someone is hitting the limit.

02Try it

This is the same algorithm, running in your browser: 5 requests per 10-second sliding window.

03The design

Each user's recent requests live in a Redis sorted set, scored by timestamp. A check is three steps: remove entries older than the window (ZREMRANGEBYSCORE), count what's left (ZCARD), and if there is room, add the new request (ZADD). The steps run atomically, so two instances can't both hand out the last slot.

When a request is rejected, the service publishes a breach event to SQS for downstream alerting and analytics. CloudWatch tracks the service itself.

04Trade-offs

Fixed window counter rejected

One counter per minute is the cheapest option. But a client can send a full quota at 11:59:59 and another at 12:00:00, doubling the limit across the boundary.

Token bucket considered

Great when you want to allow short bursts. I wanted a hard, easy-to-explain rule: no more than N in any window.

Sliding window in a Redis sorted set chosen

Exact, with no boundary burst, and capacity returns smoothly as requests age out. It costs more memory per user than a counter, which is acceptable for per-user API limits.

Send alerts inside the request rejected

Simple, but it ties the latency of every rejected request to the alerting system's health.

Publish breach events to SQS chosen

The request returns immediately; alerting and analytics consume events at their own pace and can fail without affecting traffic.

05Results

  • Per user / IPthrottling shared across instances
  • Sliding windowno double quota at window edges
  • Asyncbreach events via SQS
  • AWSEC2, ElastiCache, CloudWatch

06What I'd do next

  • Decide what happens when Redis is unreachable: fail open (availability) or fail closed (protection), per route.
  • Standard headers such as Retry-After and remaining-quota, so well-behaved clients can back off on their own.
  • A cheaper approximate mode (sliding window counter) for very high-volume, low-stakes limits.
