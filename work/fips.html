SECURITY ENGINEERING

Making FIPS compliance fail loudly at startup

Regulated customers need FIPS-validated cryptography. I integrated the Bouncy Castle FIPS provider into the platform and moved validation to JVM startup, so a bad configuration stops the server immediately instead of surfacing later as a runtime exception.

Role
Lead developer
Where
Progress Software
Stack
Java, JVM, Bouncy Castle FIPS, TLS

01The problem

Customers in government, finance and healthcare can only run software that uses FIPS-validated cryptography. Supporting it means more than adding a library: every algorithm, key store and TLS setting has to come from the approved set.

The painful part was how failures showed up. A server could start cleanly with a non-compliant setting and run fine until the first code path touched it. Then it threw a security exception that named an algorithm, not the setting that caused it.

02Constraints

  • Existing deployments must keep working. FIPS mode had to be something customers turn on, not something that breaks their upgrade.
  • Crypto errors are hard to read. The person who sees the error is usually an administrator, not a cryptographer.
  • Zero tolerance for regressions in the code that protects every connection.

03The design

  • Bouncy Castle FIPS as the cryptographic provider, integrated into the platform.
  • Proactive FIPS validation at JVM startup. Before the server accepts a connection, it checks that the provider is in place and that the configured algorithms and key stores are approved. If not, it stops and says which setting to change.

04Trade-offs

Document the requirements and let it fail at runtime rejected

No code to write, and how it worked before. But the feedback arrives late, in production, as an exception most people can't interpret.

Silently fall back to a non-FIPS algorithm rejected

Keeps the server up, and quietly breaks the compliance the customer is paying for. The worst option of the three.

Validate at startup and refuse to run chosen

A stricter server is slightly more annoying to configure the first time. In exchange, a wrong setting is caught by the person deploying it, with a message that tells them what to fix.

05Results

  • −40%security exceptions
  • +30%client security adoption
  • 20+CVEs remediated, including critical RCEs
  • 0production regressions

06What I'd do next

  • A dry-run command that validates a configuration without starting the server, for CI pipelines.
  • Crypto agility: make swapping algorithms a configuration change, ready for post-quantum requirements.
