ARCHITECTURE

Shipping security fixes without waiting for a release train

The application server shipped inside a monolithic LTS release, so a fix for any of its 200+ third-party libraries had to wait for the next one. I led the architecture that made the server version-independent.

Role
Architecture lead
Where
Progress Software
Stack
Java, Tomcat, PASOE

01The problem

PASOE, the application server, shipped as part of the platform's LTS release. That's a sensible default: one version number, one test matrix, one install.

It stops being sensible when a critical CVE lands in one of the 200+ third-party libraries the server depends on. The fix might be a one-line version bump, but it could only reach customers inside the next platform release.

02Constraints

  • LTS customers upgrade rarely, on purpose. Whatever we built had to work with the platform version they already run.
  • Two versions now have to agree. A newer server talking to an older platform (or the reverse) must never fail in a confusing way.
  • No big-bang migration. Customers needed a way to adopt this gradually and to back out.

03The design

Two pieces made it work:

  • A cross-version negotiation protocol. On connect, the server and the platform tell each other which versions and capabilities they support and settle on a common set. An unsupported pairing is refused up front with a clear reason, rather than failing halfway through a request.
  • A phased rollout strategy. Independent versioning started as opt-in, so early adopters could prove it in their own environments before it became the default.

04Trade-offs

Hotfix every supported LTS release rejected

No architecture change needed, but the work multiplies: every fix times every supported release, each needing its own build and test cycle. It gets slower exactly when speed matters.

Bundle fewer libraries rejected

Shrinks the problem without solving it. The libraries that remain still can't be patched on their own.

Version the application server independently chosen

One fix, shipped once, usable across platform versions. The price is a compatibility contract we now have to maintain and test, which is what the negotiation protocol is for.

05Results

  • 200+third-party libraries can get security updates independently
  • Decoupledfrom the monolithic LTS release cycle
  • Phasedrollout, no forced migration

06What I'd do next

  • Automated compatibility matrix: test every supported server and platform pairing on each build.
  • Dependency freshness as a dashboard, so "how exposed are we right now?" has an answer without a meeting.
