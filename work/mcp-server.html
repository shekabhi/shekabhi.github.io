AI INFRASTRUCTURE · SECURITY

Letting AI agents use enterprise APIs, safely

AI agents are only useful if they can act on real systems. I architected the OpenEdge MCP Server, which turns existing REST APIs into tools an agent can discover and call, without ever handing it a password.

Role
Architect and lead developer
Where
Progress Software
Stack
Java, MCP, OAuth2 + PKCE, JWT/JWKS, Docker

01The problem

Enterprises have years of business logic behind REST APIs. AI agents can reason well, but they can't use an API they've never seen, and a human copy-pasting between a chat window and an admin screen isn't automation.

The Model Context Protocol (MCP) gives agents a standard way to discover and call tools. The hard part isn't the protocol. It's that an agent acting on someone's behalf is a new kind of client: it's not a browser, it can't keep a secret reliably, and it will try whatever a prompt tells it to.

02Constraints

  • Don't change the existing APIs. Customers already run them in production.
  • No shared secrets. An API key pasted into an agent's configuration is one prompt injection away from leaking.
  • Least privilege per tool. Reading a customer record and creating an order shouldn't need the same permission.
  • Deployable by ops teams who have never heard of MCP.

03The design

The server sits between the agent and the REST API. It describes each endpoint as a tool with a typed input schema, and every tool call has to carry a signed, scoped token. Step through a full call below.

Three checks happen on every call before anything reaches the API: the token's signature (against the auth server's public keys, fetched as JWKS and cached), its expiry and audience, and whether its scopes cover the specific tool being called.

04Trade-offs

Static API keys rejected

Simplest to build, and what many early MCP servers did. But a key can't be scoped per user, can't be revoked per session, and lives in a config file an agent can read.

OAuth2 client credentials rejected

Fine for service-to-service calls, but the agent would act as itself, not as the user. Every action would look the same in the audit log.

OAuth2 Authorization Code + PKCE chosen

The user signs in and approves scopes; the agent never sees a password. PKCE means the agent doesn't need a client secret, so there is nothing long-lived to steal.

Hand-written tool for each endpoint rejected

Gives the nicest descriptions, but every new endpoint would need new code, and the tools would drift from the API.

Tools generated from the API's own description chosen

New endpoints become tools without new code. The cost is that tool quality depends on how well the API is documented, so descriptions can be overridden where it matters.

05Results

  • No secretsshared with agents, thanks to PKCE
  • Per toolscope-based access control
  • Dockerproduction deployment pipeline

Existing REST APIs became usable by AI agents without changing them, with enterprise security (JWT/JWKS, OAuth2 + PKCE, scope-based access control) and a containerized deployment path.

06What I'd do next

  • Human approval for risky tools. Let destructive calls pause for a confirmation instead of relying on scopes alone.
  • Per-tool rate limits, because an agent in a loop is a very efficient way to overload an API.
  • Audit trails built for agents: which prompt led to which call.
